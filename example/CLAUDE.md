# CLAUDE.md

## 1. Steering ファイル運用方針 (`.steering/`)

### 参照

- 非自明な調査・障害対応・設計判断を伴うタスクに着手する前に、`.steering/` 配下に関連しそうな既存ファイルがないか確認する。関連があれば読んでから作業を始める。
- 既存の steering ファイルは「著者の当時の結論」であり、常に正しいとは限らない。内容を鵜呑みにして検証を省略せず、「この文書に書かれていない原因はないか」を意識して読む。

### 作成タイミング

- バグ調査、原因不明の障害対応、設計判断を伴う実装など、後から経緯を追う価値があるタスクでは、着手時点で `.steering/YYYY-MM-DD-短い英語スラッグ.md` を新規作成する。
- 単純な修正・タイポ直し・小さなリファクタリングには不要。

### 書き方

- 冒頭に `日付` / `関連`（過去の steering ファイルへの `[[ファイル名]]` リンク）/ `ステータス` を明記する。
- 作業完了後にまとめて書くのではなく、**調査の途中経過をリアルタイムで追記していく**（仮説→検証→棄却/採用の過程を残す）。
- 仮説が誤りだと判明した場合は記述を削除・上書きせず、「訂正」として残す（誤りに至った経緯も後から追える価値がある）。
- 含める観点の目安：発端・現象／調査した仮説とその検証結果（棄却したものも含む）／確定した原因／修正内容／テスト／実機検証などの検証ログ／残存リスク・未解決事項。
- 作業中に新しい確認事項や副次的な問題が見つかった場合は、元の調査範囲外でも追記する。

## 2. Knowledge ファイル運用方針 (`.knowledge-index/`)

### 三層の役割分担

- `docs/` は記憶ではなく**成果物**である。現在の正しい状態を示す完成品であり、読めば分かることをここに置く。Steeringで確認された現在状態は、必要に応じて `docs/` へ反映する。
- `.steering/` は**記憶そのもの**である。経験・経緯・プロセスの時系列記録（1節参照）。
- `.knowledge-index/` は `.steering/` という記憶を検索可能にする**インデックス**である。`docs/` の複製ではない。

### 記載する前の判定基準

- 書く前に「これは `docs/` を見れば分かることではないか」を自問する。済むなら書かない。
- `docs/` が意図的に書かない領域（経緯・トラブル解決・変遷の歴史）のみを対象とする。
- 複数箇所の情報をまとめ直しただけのものは、一見「横断的な洞察」に見えても `docs/` の複製に過ぎないため書かない。
- 「既にどこかに書いてある」と判断する際は、その"どこか"がチーム共有される場所（`docs/` `.steering/` `.knowledge-index/`）か、個人のローカル環境限定の情報（`memory/` 等）かを必ず区別する。個人限定の情報を理由に記載を見送ってはならない。

### エントリの構成

- 1エントリ = 1トピック。見出し・関連ワード・参照先（時系列）の3要素のみで構成し、経緯の要約文は持たせない。
- 参照先は「日付＋出典ファイル＋見出しテキスト」のみとし、道案内に徹する。見出しテキストはMarkdown記法（バッククォート等）を含め、原文のまま正確に引用する（プレーンテキスト化・言い換えをしない）。実際の経緯は都度参照先を読んで確認する。
- 1トピックに複数の参照先がある場合は時系列で並べる。訂正の新旧・経緯の流れは並び順で表現し、要約で説明し直さない。
- 関連ワードは、想定される曖昧な言い回し・同義語を広めに列挙する（読み手のLLMが意味的にマッチするため、機械的な同義語辞書は不要）。
- 既存トピックに参照先を追記する際は、(a) 時系列の並び順が崩れていないか、(b) トピック名が最初の参照先だけを想定した狭い名前になっていないかを都度確認する。後者は参照先が1件のうちは気づきにくく、2件目以降を追加する時点で初めて顕在化する。
- 同じSteeringファイル・同じ見出しを複数のトピックから参照してよい。

### ファイル構成

- ファイル名やテーマを先に決めてトピックを選別しない。まず `misc.md` のような未分類の受け皿に何でも起こす。
- 内容が増えてまとまりが見えてきた時点で、初めて分割・トピック整理を検討する。

### 生成・更新のタイミング

- 自動生成はしない。人間の明示判断を介する。
- 基本運用: 新しい `.steering/` ファイルが確定するたびに、そのファイルを舐めてトピック候補を抽出し、上記の判定基準を適用した上で該当する `.knowledge-index/` ファイルに追記する。
- 収録基準は「何を拾うか」を先に決めず、実際に想定される質問（曖昧な想起、経緯の確認等）から逆算して判断する。

### 対象となる情報源

- 開発・運用フェーズで発生する依頼文・資料・指示（Backlogチケット、外部資料、チャットログ等）も `.steering/` の記録対象であり、`.knowledge-index/` の収録候補になりうる。
- 目的は、後から不具合調査・改修が入った際に「どういう経緯で今こうなっているのか」を辿れるようにすることである。
