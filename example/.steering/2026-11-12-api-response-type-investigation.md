# 会員一覧APIの仕様書と実レスポンスの型が合わない件の調査

- 日付: 2026-11-12（11/25まで同じ事象を追記）
- 関連: なし（この件の再利用例は[[2026-11-20-order-history-api-type-mismatch]]）
- ステータス: 確認待ち（`birthDate`の将来の形式は、仕様書の改訂後に`docs/`へ反映。改訂は12/1予定）

※架空の記載例です。API・項目名・担当者は実在しません。

## 発端

- 会員一覧画面の改修で、会員一覧API（`GET /members`）を呼ぶ。APIは別会社の担当で、画面側からは修正できない。
- API定義書（v1.2）の型定義は、`memberId`が数値、`points`が数値、`birthDate`が`yyyy-MM-dd`の文字列。
- 画面側は型を厳密に扱う作り（TypeScript、実行時検証あり）。仕様書の型を信じて実装し、実レスポンスの型が違うと、画面全体が例外で止まる。
- 先に実レスポンスを見る。仕様書の読み込みだけで実装に入らない。

## 実レスポンスの観測

11/12、テスト環境で20件取得した。

- 認証: 仕様書どおりのベアラートークンで取得できた。仕様書と一致。
- `name`: 文字列で返る。仕様書と一致。
- `memberId`: `"00123"`のように、先頭ゼロ付きの**文字列**で返る。仕様書は数値。
- `points`: 数値で返る。仕様書どおり。
- `birthDate`: `"1985-04-02"`のほか、`""`（空文字）が3件。

## 仮説と検証

| 仮説 | 見立て | 結果 |
|---|---|---|
| A: 仕様書が正しく、APIの実装が誤り | 先頭ゼロを保つ文字列は、意図した形にも見える | 棄却（11/14の回答） |
| B: APIの実装が正しく、仕様書が誤り | DBの列が文字型で、そのまま返している可能性 | 採用（11/14の回答） |
| C: `memberId`だけ不整合 | 他の項目は仕様書どおりに見える | 棄却（11/12、下記） |

- AとBのどちらが契約かは、API担当にしか決められない。11/12の時点では断定しない。
- 仮説Cで進めかけたが、念のため件数を増やして100件取得した。`points`が`null`の会員が7件あった。仕様書に`null`の記載はない。

## 訂正

- 「`memberId`だけ不整合」は誤りだった。`points`の`null`と`birthDate`の空文字も、仕様書にない挙動。20件では見えなかった。
- 件数を絞った観測だけで結論を出さない、という扱いにする。

## API担当への確認

11/12に先に出した（回答希望 11/18。画面の結合テストが11/25で、それまでに必要）。

1. `memberId`は文字列が正か、数値が正か
2. `points`が`null`になるのは、どういう状態か
3. `birthDate`の空文字は、未登録を意味するか
4. 仕様書とAPIのどちらを修正する予定か。時期はいつか

## 境界での扱い（案の比較）

APIを自分たちでは直せない。回答を待つ間に、画面側の境界での扱いを比較した（11/12）。

| 案 | 内容 | 判断 |
|---|---|---|
| 1 | 実レスポンスに合わせて型を決め打ちする | 回答が逆なら全面やり直しになるため見送り |
| 2 | 境界で検証し、想定外の型はエラーとして扱う | 採用。回答が出ても修正が小さい |
| 3 | 境界で型を変換して吸収する | 仕様が確定していないものを変換する根拠がない。保留 |

案2の検証と、テストケース（`null`・空文字・先頭ゼロ）を先に作った。テスト環境の100件に対して実行し、想定外の型は検証エラーになることを確認した。

## docsへの反映（11/12）

- 仕様が確定していないため、`docs/API_CONTRACT.md`には、仕様書と実レスポンスの一致を確認できた項目（URL・認証・`name`）だけを書く。
- `memberId`・`points`・`birthDate`は、回答後に書く。

## 11/14 回答

新しいセッションで再開した。MEMORYの引き継ぎメモを読み、このSteeringの11/12までの記録を確認した。コードも確認し、記録と一致することを確認した（`null`・空文字・先頭ゼロの3ケース）。回答待ちが残っていたため、回答の有無から確認した。

API担当の回答:

1. `memberId`は文字列が正。**仕様書の誤り**（仮説Bを採用、Aを棄却）
2. `points`の`null`は、ポイント制度の未加入を意味する
3. `birthDate`の空文字は、未登録を意味する。ただし、将来`null`に変える可能性がある
4. 仕様書を修正する。12/1予定

## 11/14 判断

- `memberId`は文字列、`points`は「数値または`null`（未加入）」として確定。`docs/API_CONTRACT.md`に反映した。
- `birthDate`は、将来`null`に変わる可能性が示されたため、確定仕様としては`docs/`に書かない。
- 境界で型を変換して吸収する案3は、引き続き採用しない。検証してエラーにする案2を維持する。
- 回答を反映した境界の検証（`memberId`は文字列、`points`は数値または`null`）で、テスト環境の100件がエラーなく通ることを確認した。

## 11/25の結合テストと仕様書の改訂（12/1）の関係

11/14に整理した。11/25までに必要なのは、**APIの動作についての合意**であり、改訂後の仕様書そのものではない。動作は11/14の回答で、`birthDate`を除いて合意できている。

- 11/25の結合テストは、回答済みの動作で進める。仕様書の改訂（12/1）は待たない。
- 仕様書の改訂は、`docs/`の記載が正しいかを照合する材料として使う。
- 未合意なのは`birthDate`の将来の形式だけ。**11/22までに**API担当へ、形式の変更時期の見込みを確認する。
- 11/22までに見込みが出ない場合の暫定対応: 空文字と`null`の両方を「未登録」として受け入れる。どちらも`docs/`には確定仕様として書かない。

## 11/22 `birthDate`の将来の形式の確認

API担当へ確認した。回答:

- 未登録は、将来`null`で返す。切り替えは12/10のAPIリリース。
- 12/10以前は、これまでどおり空文字で返す。

判断:

- 暫定対応（空文字と`null`の両方を「未登録」として受け入れる）を、そのまま使う。12/10の前後で、画面側の変更は要らない。
- 切り替えの時期は仕様書の改訂（12/1予定）に載る見込み。仕様書で確認できるまで、`birthDate`は`docs/`に書かない。
- 空文字・`null`の両方を受け入れた場合の挙動を、テストケースに追加し、テスト環境で通ることを確認した。

## 11/25 結合テストの結果

- 回答済みの動作（`memberId`は文字列、`points`は数値または`null`、`birthDate`は空文字または`null`）で実施した。全件通った。
- 検証エラーの場合に、画面全体が止まらず、該当行だけがエラー表示になり、ログに記録されることを確認した。
