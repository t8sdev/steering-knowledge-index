# 会員一覧APIの仕様書と実レスポンスの型が合わない件の調査

## 発端

- 会員一覧画面の改修で、会員一覧API（`GET /members`）を呼ぶ。APIは別会社の担当で、画面側からは修正できない。
- API定義書（v1.2）の型定義は、`memberId`が数値、`points`が数値、`birthDate`が`yyyy-MM-dd`の文字列。
- 画面側は型を厳密に扱う作り（TypeScript、実行時検証あり）。仕様書の型を信じて実装し、実レスポンスの型が違うと、画面全体が例外で止まる。
- 先に実レスポンスを見る。仕様書の読み込みだけで実装に入らない。

## 実レスポンスの観測

テスト環境で20件取得した。

- 認証: 仕様書どおりのベアラートークンで取得できた。仕様書と一致。
- `name`: 文字列で返る。仕様書と一致。
- `memberId`: `"00123"`のように、先頭ゼロ付きの**文字列**で返る。仕様書は数値。
- `points`: 数値で返る。仕様書どおり。
- `birthDate`: `"1985-04-02"`のほか、`""`（空文字）が3件。

## 仮説と検証

| 仮説 | 見立て | 結果 |
|---|---|---|
| A: 仕様書が正しく、APIの実装が誤り | 先頭ゼロを保つ文字列は、意図した形にも見える | 未確定（API担当の回答待ち） |
| B: APIの実装が正しく、仕様書が誤り | DBの列が文字型で、そのまま返している可能性 | 未確定（API担当の回答待ち） |
| C: `memberId`だけ不整合 | 他の項目は仕様書どおりに見える | **棄却**（下記） |

- AとBのどちらが契約かは、API担当にしか決められない。この時点では断定しない。
- 仮説Cで進めかけたが、念のため件数を増やして100件取得した。`points`が`null`の会員が7件あった。仕様書に`null`の記載はない。

## 訂正

- 「`memberId`だけ不整合」は誤りだった。`points`の`null`と`birthDate`の空文字も、仕様書にない挙動。20件では見えなかった。
- 件数を絞った観測だけで結論を出さない、という扱いにする。

| 案 | 内容 | 判断 |
